# The delivery half — Phases 0–8, and the G5 merge gate

Stages A, B and C decide whether to build, what must be true, and how it will
be shaped. This file covers what happens after G4: turning a signed-off design
into merged code. It is the counterpart to `stage-a-discovery.md`,
`stage-b-definition.md` and `stage-c-design.md`, and it exists because that
half of the process had gates and commands but no written DoD, so nothing
could be checked.

Work can legitimately enter at **Phase 0** without passing through Stage A at
all — a bug fix, a small change, a compliance patch. Work that came the long
way arrives with `discovery`, `define`, `design` and `gates` already filled in
its manifest. Both are normal.

For the command sequence rather than the specification, see
`docs/ai-sdlc/cookbook.md`.

---

## Two naming schemes, and which one is normative

This framework labels the delivery half two different ways, and until now
neither document explained the other. Both appear in files that ship today:

- **Numbered phases 0–8** — used by `phases.md`, `/plan-feature`, `/spec`,
  `/review`, `/pr` and the cookbook.
- **Lettered stages P · D · E · F · O** — the back half of the eight-stage
  spine `A·B·C·P·D·E·F·O`, used by `stage-c-design.md` ("what Stage C hands to
  Stage P"), by `/gate` (G5 sits at "F3") and by `pm-analyst` (which owns
  "O1").

**The numbered phases are normative.** They are the ones with commands, exit
conditions and a manifest. The letters are aliases that appear in a handful of
places, and only some of them have a definition anywhere in this repository.

| Letter | Evidence inside this repo | Covers | Status |
|---|---|---|---|
| `P` | `stage-c-design.md`: *"Stage P mirrors these into the repo plane and breaks the SRS into executable tasks"*; `gate.md`: *"stage P after G4"* | Phases 0–3 | Scope confirmed, name not |
| `D` | none | Phase 4 | `[chưa xác nhận]` — assigned by elimination |
| `E` | none | Phases 5–6 | `[chưa xác nhận]` — assigned by elimination |
| `F` | `gate.md` + `traceability.yaml`: G5 is *"end of F3"* | Phases 7–8 | `F3` = the merge point, confirmed. `F1`/`F2` not defined here |
| `O` | `pm-analyst.md`: owns `O1`, described as *"triage feedback"* | after merge | `O1` confirmed, the rest not |

**What this table is honest about.** `D`, `E` and the expansion of the letters
are inferences from position, not definitions anybody wrote down. They carry
the `[chưa xác nhận]` marker required by C-5 and they must keep it until the
author of the original specification confirms them. Do not quietly promote an
inference to a fact by deleting the marker.

> **One gap the letters expose that the numbers hide.** `G5` is recorded as
> the end of **F3**, which implies `F1` and `F2` before it, while the numbered
> scheme has only Phase 7 (PR) and Phase 8 (merge) — two steps where the
> letters imply three. Project notes outside this repository describe `F2` as
> *"đóng traceability & publish bản người đọc"* (close traceability and
> publish the reader-facing version). No such step exists in the numbered
> phases, and `README.md` independently records that automatic publishing of
> artefacts to Confluence is **not built**. These are very likely the same
> hole seen from two directions. Phase 7.5 below records it as an open
> obligation rather than pretending the sequence is complete.

`P` is also overloaded three ways across this codebase, which is worth knowing
before you read a `P<n>` anywhere: a **prompt id** (`/review` says "apply
prompt P5"), a **severity level** (`/audit` outputs "P0/P1/P2 severities"),
and this **stage letter**. Only the third is a phase. Nothing renames them
here, because renaming touches nineteen files; this note is so a reader is not
misled.

## Ownership

| Phase | Produces | Who drives | Command |
|---|---|---|---|
| 0 | `traceability.yaml` | whoever intakes the work | generated by `/plan-feature` |
| 1 | `plan.md` | engineer + architect if cross-cutting | `/plan-feature <slug>` |
| 2 | `spec.md` | engineer | `/spec <slug>` |
| 3 | ADR, only if architectural | **FS 20 Architect** | `/adr <slug>` |
| 4 | code + tests | **FS 2 Client Engineering** | project-specific |
| 5 | review findings | an agent that did **not** write the code | `/review <slug>` |
| 6 | STRIDE table | **FS 14 AppSec** | `/security-review <slug>` |
| 7 | pull / merge request | engineer | `/pr <slug>` |
| 7.5 | traceability closed, reader copy published | engineer | **not built** — see below |
| 8 / G5 | merge | **a human, never the harness** | `/gate G5`, then `/notify-merge` |

## Phase 0 · Intake

**In** — a ticket, a G4 sign-off, or a bug report.

**Do** — generate the manifest. Identify every source the work depends on and
check each one is current, not merely present.

**Out** — `docs/specs/<slug>/traceability.yaml`
(`vnd.ai-sdlc.traceability/v3`).

**Done when** — all four hold:

1. Every source is **named and dated**. A source with no date cannot be shown
   to be current.
2. Scope is written down, including what is **out** of scope.
3. Work that came through Stage A–C carries its `discovery`, `define`,
   `design` and `gates` blocks; work that entered here **omits those blocks
   entirely** rather than filling them with `PENDING`.
4. The ticket key is recorded if one exists, `Không có` if not.

Item 3 is the one that goes wrong. A manifest padded with `PENDING` for stages
that never ran is indistinguishable from one where those stages are genuinely
outstanding, and `/gate` cannot tell the difference either.

---

## Phase 1 · Plan

**In** — the manifest.

**Do** — break the work into sub-tasks. Name what is unknown instead of
guessing it.

**Out** — `docs/specs/<slug>/plan.md`.

**Done when** — sub-tasks are listed with a task id each, every open question
is **explicit and owned**, and no sub-task depends on an answer that does not
exist yet. A plan that reads as though everything is known, when it is not, is
the failure this phase exists to prevent.

---

## Phase 2 · Spec

**In** — the plan, plus the SRS if the work came through Stage C.

**Do** — specify behaviour precisely enough that someone can write a failing
test from it without asking a question.

**Out** — `docs/specs/<slug>/spec.md`.

**Done when** — all three hold:

1. **A failing test can be written from it** — the literal bar, the same one
   the PRD uses at B2. Hand it to someone who was not in the conversation.
2. Every requirement carries an id, and every id traces up to an `FR-###` from
   the SRS or, for Phase-0 entries, to the ticket.
3. Error and edge behaviour is specified, not just the happy path.

---

## Phase 3 · ADR, when the decision is architectural

**In** — the spec.

**Do** — only when the work changes a public API, a persistence shape, a
layer boundary, or the security posture. Most work does not need one; opening
an ADR for a bug fix is noise that makes the real ADRs harder to find.

**Out** — `docs/ai-sdlc/adr/<n>-<slug>.md`.

**Done when** — **at least two real options** are compared, the decision is
recorded with its consequences, and the rejected option is described well
enough that a reader can tell it was actually considered. One option written
up as a decision is a rationalisation, not an ADR.

---

## Phase 4 · Implement

**In** — spec, ADR if any, and the design set if the work came through Stage C.

**Do** — implement against the spec. Touch only the paths the manifest names.

**Out** — code and tests.

**Done when** — all four hold:

1. **The project's own test command passes** — resolved by the
   `project-toolchain` skill, never assumed. `flutter test` is not a universal
   truth.
2. Every task id in the manifest moves to `done` or `dropped`, with a reason
   recorded for each drop.
3. New behaviour has a test that **fails without the change**. A test that
   passes against both versions tests nothing.
4. Nothing outside the manifest's declared paths changed, or the manifest was
   updated to say why.

---

## Phase 5 · Self-review

**In** — the working diff.

**Do** — walk `docs/ai-sdlc/review-checklist.md` section by section against
every changed file.

**Out** — a findings table: file, line, severity, what is wrong.

**Done when** — **no `block` or `major` finding is left unresolved**, and
every finding cites `file:line`.

> **Dispatch an agent that did not write the code.** A reviewer that helped
> write the change rediscovers its own assumptions and finds them sound. This
> is the same rule as the B1 reviewer pass, and it fails the same way when
> ignored.

---

## Phase 6 · Security review

**In** — the diff, plus the Stage C threat model if one exists.

**Do** — walk `docs/ai-sdlc/security-checklist.md` end to end and produce a
STRIDE table for anything the diff newly exposes.

**Out** — a STRIDE table with a residual risk per row.

**Done when** — **no high residual risk is left without a named follow-up**,
secrets scanning has run over the diff *and its history*, and every new
external input names where it is validated.

The history clause is not pedantry. A secret removed in the working tree but
still present in an earlier commit is still leaked; a real audit of `dchat`
found credentials across nine to eleven commits exactly this way.

---

## Phase 7 · Pull / merge request

**In** — a clean diff that passed Phases 5 and 6.

**Do** — open the PR or MR with the template filled.

**Out** — a pull request (GitHub) or merge request (GitLab), per the `vcs`
setting in `project.yml`.

**Done when** — all four hold:

1. Every section of `docs/ai-sdlc/templates/pull-request.md` is filled — no
   placeholder left, `Không có` where a section does not apply.
2. **CI is green where CI exists.** Where it does not, the PR says so; a
   missing pipeline is reported as missing, never as passing.
3. The PR body cites the manifest's task ids and the ticket key.
4. A reviewer is requested — a named person, not the author.

## Phase 7.5 · Close traceability and publish the reader copy — NOT BUILT

**This phase has no command and no template.** It is recorded here because the
obligation exists and is currently met by nobody:

- the manifest's `tasks` block should be closed out and the trace from
  `BR-001` through to the merge request made complete and readable;
- the reader-facing copy of the artefacts should reach Confluence, where the
  people who are not in the repository can see them.

`README.md` records the second half as not built: only `/gate` calls
`create_confluence_page`, so Stage A/B/C artefacts reach the manifest and stop
there. The lettered scheme appears to call this step `F2`
(`[chưa xác nhận]`, see the naming table above).

**Until it is built, the honest position is that the trace ends at the
manifest and the wiki is updated by hand.** Do not describe the pipeline as
publishing artefacts automatically.

## Phase 8 / G5 · Human merge — HARD GATE

**The harness never merges.** It has no merge tool, by design, and `/gate G5`
records only that a person did.

| Decision | Meaning |
|---|---|
| `MERGED` | a human approved and merged |
| `CHANGES-REQUESTED` | review returned it; the branch stays open |
| `CLOSED` | abandoned without merging, with a reason |

**Required evidence** — `/gate` refuses a G5 record missing any of:

1. `mr_url` — the pull or merge request, so the decision has an artefact.
2. `approved_by` — **a named human.** Never the harness, never "AI", never a
   bot account. If the only approver is automation, G5 has not happened.
3. `minutes` — the same rule as every other gate: a decision with no record is
   hearsay.

**Done when** — the decision is recorded, the manifest's `status` moves to
`shipped` on `MERGED`, and `/notify-merge` has run. Nothing else in the
pipeline knows a merge happened, because the harness did not do it — so the
announcement is not optional politeness, it is how the next stage finds out.

## After merge · the feedback return path

`pm-analyst` owns `O1`, described in its own agent file as triaging production
feedback back into the process. The route is:

```
production signal → O1 triage → the stage that owns the defect
```

A defect in a business rule goes back to **B1**, not to a patch. A defect in a
requirement goes back to **C2**. Only a defect in the code goes back to
**Phase 4**. Routing everything to Phase 4 is how a wrong rule gets
implemented correctly three times.

This return path has an owner and a described job but **no command and no
DoD**. It is the least specified part of the framework and should be read as a
sketch, not a contract.

## What the delivery half still owes

Written plainly so it is not rediscovered as a surprise:

| Gap | Consequence |
|---|---|
| Phase 7.5 has no command | The trace ends at the manifest; Confluence is updated by hand |
| `O1` has no command or DoD | Feedback routing depends entirely on who is on duty |
| `D`, `E` and the letter expansions are unconfirmed | Two vocabularies for one process; this file is the only bridge |
| No delivery-half equivalent of `check-conventions.py` for `plan.md` / `spec.md` | Phase 1 and 2 DoDs are read by people, not checked by a machine |

Every row above is a real obligation with no owner. None of them is a reason
to stop using the delivery half — Phases 0–8 have commands that work — but
each one is a place where "the process says so" currently means "somebody
remembered".
