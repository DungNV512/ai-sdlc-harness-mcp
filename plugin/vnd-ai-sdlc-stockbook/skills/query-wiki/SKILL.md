# Query Wiki Skill

Search and answer questions from the compiled `docs/wiki/` layer, citing the exact
artifact and upstream source. This is a read-only skill — it never writes a
file (see `digest-wiki` for that).

This is a rewrite for stockbookapp: the mother repo's version of this skill
answered from a knowledge-graph database via dedicated graph-query calls.
All knowledge is stored in plain markdown files on disk — the workflow below is: grep/glob
over `docs/wiki/**/*.md` frontmatter and bodies, then synthesize and cite.

## When to Use

- "What do we know about X?"
- "Summarize everything related to Y"
- "Compare A and B based on what's already compiled"
- Any question answerable from `docs/wiki/` without fetching anything new

Do NOT use this skill to pull new content from Confluence/Jira (`pull-confluence`,
`pull-jira`) or to write a new synthesized artifact (`digest-wiki`).

## Architecture

```
User question -> Grep wiki/**/*.md (topic, title, body)
              -> Read matching file(s) frontmatter + body
              -> Read sources.json for upstream_refs' `stale` status
              -> Answer, citing artifact_id + upstream URL + staleness
```

`docs/wiki/index.md` (generated by `bin/generate-wiki-index.py`) is a fast
first stop for browsing by topic heading; `sources.json` is the one place
that has staleness for every upstream source. Neither is authoritative over
the actual `docs/wiki/**/*.md` files — always read the file itself before
answering, don't just quote the index.

## Steps

### 1. Find candidate artifacts

```bash
# Browse by topic heading first (cheap, human-curated)
grep -n -i "<topic>" wiki/index.md

# Then search the actual compiled content (frontmatter `topic:` list + body)
grep -rli "<topic>" wiki/**/*.md
grep -rn "<topic>" wiki/*/*.md
```

Prefer `docs/wiki/` over `docs/raw/` for answering questions: `docs/wiki/` holds ~21
curated, one-per-topic overview artifacts; `docs/raw/` holds 182+ near-duplicate
mirrored source snapshots not meant for casual reading (see `use-kb`
for the full directory map).

### 2. Read the matching artifact(s)

Read the whole file, not just the frontmatter — the frontmatter's `sources:`
list only tells you which pages fed the artifact, the body is the actual
compiled answer.

Frontmatter fields that matter for citation (see `use-kb` for the full
field reference):

| Field | Use |
|---|---|
| `artifact_id` | The citation handle, e.g. `WIKI-SN-AUTH-001` |
| `upstream_refs` | List of `sources.json` keys (e.g. `CONF-SN-405143554`) this artifact was compiled from |
| `sources` | `{title, url}` pairs — human-readable fallback when `upstream_refs` doesn't resolve |
| `confidence_markers` | What evidence discipline was used when compiling (`EXTRACTED`, `INFERRED`, ...) |

### 3. Check staleness — MANDATORY

For every `upstream_refs` entry on the artifact(s) you're citing, look up its
current status in `sources.json`:

```bash
python3 -c "
import json
ledger = json.load(open('sources.json'))
for ref in ['CONF-SN-405143554']:  # upstream_refs from the artifact's frontmatter
    entry = ledger.get(ref)
    if entry is None:
        print(f'{ref}: not in ledger')
    else:
        print(f\"{ref}: stale={entry['stale']}  local_version={entry['local_version']}  upstream_version={entry['upstream_version']}  url={entry['url']}\")
"
```

`stale` is tri-state: `current` (local matches upstream), `stale` (upstream
has moved on), `unknown` (last staleness check couldn't reach the source —
treat like `stale` for answering purposes: don't assert it's current).
`docs/wiki/index.md`'s own "staleness: N current, M stale" summary per artifact
is the same data pre-aggregated — reading it is a fast substitute for the
per-ref lookup above when you just need the overall picture, not which
specific source moved.

**If `stale` (or `unknown`), you MUST tell the user.** A confidently-wrong
answer sourced from a stale doc is exactly the failure this whole pipeline
exists to prevent — do not silently answer from a stale artifact as if it
were current. Say so explicitly, e.g.:

> Note: this answer cites `WIKI-MI-PROFILE-001`, which has 1 stale source
> (`CONF-MI-412812537`, local v9 vs. upstream v11 as of the last
> `bin/check-staleness.sh` run). The rest of what's below may already be
> superseded by that upstream change — consider re-running
> `bin/ingest-confluence.sh 412812537` before relying on it.

If `sources.json` doesn't exist yet, or an artifact predates task #7 and
carries no `upstream_refs` at all, staleness for that artifact is
`unknown` by definition — say so rather than treating it as current.

An artifact with `origin: derived` (see `digest-wiki`) has no upstream to
be stale against — its own `docs/wiki/log.md` entry / `last_updated` field is
the only freshness signal available; say that plainly instead of reporting
a staleness verdict that doesn't apply.

### 4. Synthesize the answer

Confidence markers (mirror what the source artifact declares in its own
`confidence_markers:` frontmatter — don't invent a stronger claim than the
artifact itself makes):

- **EXTRACTED** — stated directly in the artifact's body / the upstream page
- **INFERRED** — you connected two or more artifacts/sections yourself
- **AMBIGUOUS** — artifacts disagree or the wiki text itself is unclear
- **UNVERIFIED** — from your own background knowledge, not from `docs/wiki/`

Citation format: `[artifact title](docs/wiki/<path>) (artifact_id) — upstream: <url>`.

### 5. Output

Answer in conversation. Do not write a file — that is `digest-wiki`'s job,
triggered by an explicit "save this" / "write a digest" request, not by
every question that happens to touch multiple artifacts.
